## 1. 中文攻击性 / 仇恨言论开源数据集与模型

### 关键结论

**（1）ToxiCN 确实有 target 分类，而且是四层递进标注。**
「Monitor Toxic Frame」把一条评论逐层拆成 4 个问题，对应 4 个字段（引自官方 repo README）：

| 字段 | 取值 |
|---|---|
| `toxic` | 0 非有毒 / 1 有毒 |
| `toxic_type` | 0 非有毒 / 1 一般冒犯（general offensive）/ 2 仇恨言论（hate speech） |
| `expression` | 0 非仇恨 / 1 显性仇恨 / 2 隐性仇恨 / 3 转述（reporting） |
| `target`（列表，多标签） | 0 LGBTQ / 1 地域 / 2 性别 / 3 种族 / 4 其他 / 5 非仇恨 |

- 规模：12,011 条（知乎 + 贴吧），有毒 6,461 / 无毒 5,550；其中一般冒犯 816、仇恨 5,645（显性 2,737、隐性 1,995、转述 913）。
- 附带 **1,032 词侮辱词典**，按攻击对象分 5 类（性别 / 种族 / 地域 / 反 LGBTQ / 通用脏话），且特意收录隐性侮辱（如「小仙女」）。
- 许可：**CC BY-NC-ND 4.0**（明确禁止商用）。
- 链接：论文 https://aclanthology.org/2023.acl-long.898/ ｜仓库 https://github.com/DUT-lujunyu/ToxiCN ｜提示学习版 PCR-ToxiCN（HF `UTSNLPGroup/PCR-ToxiCN`，代码 https://github.com/HTG13503/PCR-ToxiCN）

**（2）COLDataset：规模最大、最常用的中文冒犯二分类基准。**
- 37,480 条（知乎 + 微博），二分类冒犯标签；训练/验证 32,157，测试 5,323。
- 测试集额外做了 4 类细标：攻击个人 288 / 攻击群体 1,819 / **反偏见（anti-bias）668** / 其他非冒犯 2,548。
- 基线 COLDetector（bert-base-chinese）：acc 0.81、macro-F1 0.80；关键词匹配基线只有 acc 0.54 —— 证明「脏话词表过滤」远不够用。
- 标注一致性：二分类 Fleiss κ = 0.819，四分类 κ = 0.757。
- 链接：https://github.com/thu-coai/COLDataset ｜论文 https://arxiv.org/abs/2201.06025
- 许可：可访问页面上未明确写出（本环境直连 GitHub / HuggingFace 被拦），产品化前必须确认。

**（3）SWSR + SexHateLex：唯一的开源中文性别歧视数据集+词典。**
- 微博数据，两个 CSV（SexWeibo / SexComment）；ToxiCN 论文的对比表记为 8,969 条。
- **SexHateLex：3,016 条辱骂词**（部分可作隐性辱骂词表用）。
- 许可：**CC BY 4.0**（Zenodo API 确认，可商用，需署名）。
- 链接：https://zenodo.org/records/4773875 （DOI 10.5281/zenodo.4773875）

**（4）CDial-Bias：唯一把「讨论偏见」和「表达偏见」分开标的中文对话数据集——对本项目最有价值的标签设计。**
- 知乎对话，17,371 条上下文无关 + 10,972 条上下文相关（合计约 28k）。
- 标签：`Context Sensitivity`(0/1)、`Data Type`(0 无关 / 1 **bias-expressing 表达偏见** / 2 **bias-discussing 讨论/引用偏见**)、`Bias Attitudes`(0 NA / 1 **Anti-Bias** / 2 Neutral / 3 Biased)、`Topic`(种族/性别/地域/职业)、`Referenced Groups`（自由文本）。
- 规模细节：无关 12,349、表达偏见 7,659、讨论偏见 8,333；态度上 Anti-Bias 仅 454 —— 即「反偏见/批判」样本极稀疏，纯监督学习很难学到。
- 许可：仅限研究用途，其他用途需另行许可。
- 链接：https://github.com/para-zhou/CDial-Bias ｜论文 https://aclanthology.org/2022.findings-emnlp.262/

**（5）B 站相关：目前只有视频级，没有评论级。**
- **MultiHateClip**（ACM MM 2024）：YouTube + Bilibili 短视频各 1,000 条，标签 仇恨 / 冒犯 / 正常 + 片段起止 + 受害群体 + 贡献模态。中文（B 站）部分：仇恨 128 / 冒犯 194 / 正常 678；3 分类 Cohen κ 仅 0.51（中文）、二分类 0.66。80.4% 的中文有害视频依赖多模态表达。
- 链接：https://github.com/Social-AI-Studio/MultiHateClip ｜论文 https://arxiv.org/abs/2408.03468
- 其他可参考：Border of Speech（IEEE 11427346，中文冒犯言语理解基准）、中文冒犯语言数据库平台（西南民族大学，https://kjc.swun.edu.cn/info/1007/3479.htm）。二者均未逐条核实规模/许可。

**（6）关于「BATH」：未核实到任何名为 BATH 的中文 abusive/hate 数据集。**
多轮检索（"BATH Chinese hate speech dataset" 等）均无命中的论文、仓库或 HF 数据集。**不要在产品文档或代码注释里引用这个名字**，很可能是与 Border of Speech / MultiHateClip / ToxiCN 之类的名字混淆。

**（7）一个可直接用的行业事实：中文「仇恨 vs 一般冒犯」边界本身不可靠。**
ToxiCN 各层 Fleiss κ 只有 0.62–0.75；MultiHateClip 中文 3 分类 κ 0.51。**工程含义：不要做硬三分类，要做「证据分 + 阈值 + 可解释提示」。**

### 可落地建议
1. **标签体系照抄 ToxiCN 的四层**（是否毒 / 冒犯还是仇恨 / 目标群体 / 表达方式），但内部只用作打分维度，不对外输出「这是仇恨言论」的断言。
2. **词表合并**：ToxiCN 1,032（隐性侮辱强） + SexHateLex 3,016（CC BY 4.0 可商用）去重，作为「显性层」；隐性层用规则（见第 3 节）。
3. **优先用 CDial-Bias 的 `bias-discussing` / `anti-bias` 思路**做「引用批判 vs 主张」的模板，而不是自己从零定标注规范。
4. **许可红线**：ToxiCN 是 NC-ND，不能打包进商业分发；SWSR 是 CC BY，可商用但要署名；COLDataset 许可未确认，先别用于产品训练。
5. **别训练三分类模型**：先用规则+词表跑通闭环，把人工复核结果当种子数据，等有 2k+ 站内标注再谈模型。

## 2. 中文水军 / 机器人 / 控评检测

### 关键结论

**（1）公开的中文「水军」标注数据集基本没有可用的**。可引用的是三类材料：
- 执法/官方披露的真实案例特征（最贴近实战）；
- 中文专利里的特征工程（可抄）；
- 英文 bot detection 的成熟特征框架（可迁移）。

**（2）央视披露的真实水军案特征（江苏句容案，2025-03，网信办转载）**——这是最干净的「真实信号清单」：
- 用户名「大多由随机字母和数字组成」，如 `abc123`、`user456`，「明显不符合正常用户的命名习惯」；
- 评论「大多缺乏逻辑性，甚至出现大量无意义的词语组合」；
- 转发/点赞/评论「均来自同一个 IP 地址段，且操作时间间隔极短」；
- 群控软件可「输入**公式化**的评论内容」，一键转发/点赞/评论；
- 数据异常：**3 秒内 7 万转发**，不符合正常传播曲线。
- 来源：https://hbcac.gov.cn/wlgl/202503/t20250321_12865.shtml

**（3）可抄的专利特征（中文专利，直接对应工程实现）**：
- CN111191037B《基于新闻评论的网络水军识别方法和装置》：用「**评论文本相似特征**」+「**信息熵特征**」（按预设事件时间窗口 + 每条评论发布时间计算）识别水军。
- CN102571484B：把「账号所发评论为**抄袭**」直接做成特征向量的一个维度。
- 这两条正好给出两个最有效的文本侧特征：**近重复** 与 **时间熵**（发布时间过于规律 → 熵低）。

**（4）学术侧可引用**：
- 《恶意社交机器人检测技术研究》，通信学报 2017, 38(Z2):197-210，DOI 10.11959/j.issn.1000-436x.2017275 —— 中文综述，特征分类框架可参考。
- Semi-supervised internet water army detection based on graph embedding，Multimedia Tools and Applications (2022) —— 图特征（协同行为）。
- 《社交网络机器账号检测综述》（中文综述，被引记录见 cqvip 7104706213）。

**（5）B 站场景的现实约束（很重要）**：
用户脚本能拿到的字段远少于平台：**注册时间通常拿不到**，粉丝/关注数往往要额外请求接口（有风控与频次限制），IP 更不可能。所以**不要把规则设计在拿不到的字段上**。可用的代理信号：
- 等级（Lv）、UID 位数（越小越老）、头像是否默认、签名内容、粉丝/关注数（若接口可取）、历史评论的时间分布与文本分布、是否大会员/认证。

### 可落地的启发式规则（可直接实现为加权打分）

**账号侧**

| # | 规则 | 权重 |
|---|---|---|
| A1 | 昵称正则 `^[a-zA-Z]{1,6}[0-9]{2,}$`、纯数字、`用户`+数字、明显随机串 | +3 |
| A2 | 同批账号昵称共享前后缀（批量生成痕迹） | +2 |
| A3 | 等级 ≤ 2 且 24h 内发言 ≥ 8 条 | +2 |
| A4 | 头像为平台默认头像，或头像感知哈希（dHash）在同批中近重复（≥5 个号同图） | +3 |
| A5 | 关注/粉丝 > 10 且 粉丝 < 100 | +2 |
| A6 | 签名为空或与同批账号签名完全一致 | +1 |
| A7 | 24h 发言 ≥ 30 条，或相邻两条评论间隔标准差 < 3s | +3 |

**文本侧**

| # | 规则 | 权重 |
|---|---|---|
| T1 | SimHash(64bit) 汉明距离 ≤ 3 的评论，同一视频下由 ≥5 个不同账号发出 | +3 |
| T2 | 去掉数字/@/表情后「骨架」完全相同（模板化），≥3 条 | +2 |
| T3 | 长度 < 6 字且 24h ≥ 20 条 | +2 |
| T4 | 同一 emoji 连续 ≥3 次，或 emoji/字符比 > 0.4 | +1 |
| T5 | 单条 @ ≥ 5 人，或「一个 @ + 无关内容」 | +2 |
| T6 | 与同视频下已有高赞评论 CER（字符错误率）< 0.1（复制粘贴） | +2 |
| T7 | 发布时间规律性：把时间戳分箱算熵，熵 < 阈值（对应专利的信息熵特征） | +2 |

**协同侧**

| # | 规则 | 权重 |
|---|---|---|
| C1 | 同视频下 5 分钟内 ≥3 个候选账号发近重复文本 | +2 |
| C2 | 多个账号对同一组目标（评论/视频）行为序列高度重合 | +2 |

**判定策略**：总分 ≥ 6 → 「疑似」，只折叠/降权 + 显示原因；≥ 9 → 「高置信」，默认折叠但保留一键展开。**不要自动拉黑**——A4/A7 这类规则在网吧、共用设备、粉丝打投场景下的误伤概率不低。

### 可落地建议
1. **先做 T1（SimHash 近重复）**：实现成本最低、命中率最高、可解释性最好，一个视频评论区就能跑。
2. **A1 昵称正则 + A3 等级/频率组合**作为账号侧主力，**不要**依赖注册时间。
3. **把「时间局部性」写进规则**：单看文本重复会误伤「复读机」正常玩梗，加上「同视频、5 分钟窗口、多账号」才成立。
4. **输出必须带证据串**（命中了哪条规则、原文片段），否则用户不敢用。
5. **每条规则单独记录命中率与用户「误判申诉」率**，按周调权重——这是这类工具能长期活下去的关键。

## 3. 反串 / 帆船 / 理中客 / 阴阳怪气识别

### 关键结论

**（1）没有可白嫖的中文「阴阳怪气」分类器；但 2026 年有了一个高质量诊断基准，且它给出的结论极其有用。**
《You Really Didn't Get That? Benchmarking Social Pragmatic Inference for Indirect and Playful Chinese Online Comments》(arXiv 2609.04384, 2026-09)：
- 从 20 万+ 条知乎/豆瓣/小红书/贴吧互动记录中构建 **4,735 条人工校验诊断题**；
- 人类准确率 **90.8%**，最强模型 81.42%，8 个模型平均仅 **68.70%**；
- **去掉上下文（只看目标评论），平均准确率下降 39.07 个百分点，掉到 29.63%**。
- 失败模式：模型倾向「净化」语义（把阴阳怪气读成正能量/建设性批评）、认得出「在玩梗」但认错机制、错估语气强度。
- 链接：https://www.alphaxiv.org/abs/2609.04384
- **工程含义：任何「只看单条评论」的阴阳怪气判定都不可靠，必须带父评论/标题/楼中楼上下文；并且这件事的上限就是「提示」而非「判决」。**

**（2）相关但不同的资源**：
- 中文讽刺计算评测任务（GitHub `pjzj220113/chinese-sarcasm-calculation`）——存在，但 README 我这边取不到（404），规模/许可未核实。
- 黑话/隐语：「newspaper eat = not tasty」Chinese coded language taxonomy & benchmark（arXiv 2601.19932, ACL 2026）——专门讲中文评论里的编码化表达（谐音、拆字）。
- 谐音规避：Lost in Pronunciation（arXiv 2507.07640）——拼音替换型脏话规避，可直接用于生成变体规则。

**（3）四类现象的特征清单（可直接做成规则/词表）**

| 类型 | 强信号 | 弱信号 |
|---|---|---|
| **阴阳怪气** | 括号注释 `(笑)` `(不是)` `(狗头)` `(划掉)` `(误)`；与文本极性冲突的表情 `doge/🐶/😅/🙂/👏/🤡`；敬语反用「您可真行」；引号反用「"专家"」；夸张赞美+负面语境 | 语气词 `呢/哦/呀/哈/呵/呗/罢了/而已`；反问 `难道/怎么不/凭什么`；流行语 `典/急了/孝/绷/乐/赢/遥遥领先/属于是` |
| **反串（帆船）** | 账号历史立场与当前发言**自相矛盾**；过度夸张地模仿对方话术；自曝「友军」「我反串的」；结尾狗头/括号 | 单条文本内几乎不可判——**必须用账号历史** |
| **理中客** | 「客观来说/理性讨论/不吹不黑/就事论事/两边都有问题/我中立」+ 紧随其后只贬一方（**结构矛盾**） | 「理中客」一词本身在站内已是贬称，出现即带元信息 |
| **反讽** | 字面褒义 + 语境负向；程度夸张（「真的绝了」「史上最强」） | 感叹号堆叠、重复标点 |

### 可落地建议
1. **三层实现**：(a) 词表/正则打分（毫秒级，覆盖 70% 明显案例）→ (b) 字面义 vs 上下文义的向量夹角（差距大 → 反讽候选，用第 5 节的 bge-small）→ (c) 需要账号历史的（反串）单独走账号维度。
2. **括号注释和"极性冲突表情"是最值钱的两个特征**，优先做，误报率低。
3. **必须带上下文**：至少取父评论 + 视频标题；有条件取楼中楼前 3 条。这是 2609.04384 用 39 个百分点换来的结论。
4. **只做「解释性提示」，不做拉黑依据**：阴阳怪气是正常网络表达，误判代价（用户被误拉黑）远高于漏判。
5. **自建「阴阳怪气种子集」**：把用户手动标记的案例存下来，按季度扩充词表——这类现象漂移极快，词表必须可热更新。

## 4. 区分「引用/批判」与「主张」的工程手段

### 关键结论

**（1）学术界已经在标注层面把这件事拆开了，照抄即可**：
- ToxiCN 的 `expression = reporting`（913 条）：只记录/谴责针对少数群体的攻击，发布者本人不表达仇恨 —— 这正是「引用」。
- CDial-Bias 的 `Data Type = bias-discussing`（8,333 条）vs `bias-expressing`（7,659 条），再加 `Bias Attitudes = Anti-Bias`（454 条）—— 这是「引用/讨论/批判」的三分。
- **结论：不要试图只靠规则做，先按这个标签体系定义你的内部三类：主张 / 引用转述 / 批判反对，然后规则只用来给这三类打分。**

**（2）五个信号层（按信噪比排序）**

| 层 | 信号 | 处理 |
|---|---|---|
| L1 形式标记 | 中文引号 `“”`、单引号 `‘’`、书名号 `《》`、直角引号 `「」『』`、引用块 `>`、`//@`、转发语 | 引号内命中的辱骂词**降权到 0.2–0.3** |
| L2 转述动词 | 说、称、表示、认为、声称、宣称、号称、扬言、据…、听说、有消息称、网传、原文是、他的意思是 | 命中 → 标记「引用域」，域内降权 |
| L3 否定/反驳 | 不、没、没有、并非、绝非、未、别、勿、谈不上、算不上、不至于、不能苟同、反对、反驳、辟谣、澄清、离谱、恶心、无语 | 命中 → 标记「批判域」，**不降权但要单独计数** |
| L4 转折 | 但、但是、然而、不过、其实、实际上、说白了、说到底、依我看、我觉得 | **转折之后才是主张**；转折前的内容降权 |
| L5 人称/立场 | 我认为/我看/支持/反对（主张）；他/他们/有人说/某些人（引用） | 第一人称 + 评价词 → 主张 +权重 |

**（3）否定词作用域（negation scope）的可行算法**
- 触发：命中否定 cue。
- 作用域：从 cue 向右，**遇到第一个标点（，。！？；：）或转折词或引号闭合即终止**，并设最长窗口 N≈12 字（中文否定辖域通常很短）。
- 作用域内命中辱骂词 → 该词不计入或降权 0.3。
- 反向：`不是…吗`、`难道不…` 属于反问，**不构成否定**，要单独识别（反问 cue：难道、岂、何尝、何必、怎么会、不是吗、吧）。
- 可引用方法学：Chinese negation and speculation detection with conditional random fields（Yang 等）；Detecting negation and scope in Chinese clinical notes using character and word embedding（JBI 2017）—— 中文否定/推测识别的主流做法仍是「cue 词表 + 作用域窗口 + 序列标注」。

**（4）可直接用的中文转折/连接词表：Chinese-DiMLex**
- **137 个中文话语连接词**，带 5 层信息：形态变体、词性、**PDTB 3.0 语义关系**、用法例句、英文翻译；提供 XML 与网页检索。
- 出处：CODI 2023（ACL 2023 Workshop），https://virtual2023.aclweb.org/paper_CODI_13.html ；扩展版见 LRE 2024（DOI 10.1007/s10579-024-09761-9）。
- **这是目前唯一可直接下载、覆盖转折/因果/条件等关系的机器可读中文连接词库**，用它替代自己手写「但是/然而」列表。

**（5）否定词表可直接用的来源**：HowNet《情感分析用词语集》（含否定词、程度副词）以及各类汇总仓库（如 GitHub `DavionWu2018/Sentiment_dictionary`，把否定词表/程度副词/停用词打包在一起）。

### 可落地建议
1. **L1 引号 + L4 转折先做**：两条规则就能挡掉大量「引用他人言论被误判」的误伤。
2. **实现一个 `scope(text, cue)` 函数**：返回作用域区间，辱骂词落在引用域/否定域内就不计入主分——这是整个判定逻辑里性价比最高的一个函数。
3. **把「转折后」当主张区**：`但/然而/不过/其实/说白了` 之后到句末的片段，权重 ×1.5。
4. **反问句单独建表**，避免「难道不恶心吗」被当成否定而漏判。
5. **不要用通用停用词表做删词**（见第 6 节）：哈工大/百度停用词表里包含「但是、然而、不、没」等，删完你的 cue 全没了。要做的是**「cue 白名单」而不是「停用词黑名单」**。

## 5. 轻量中文语义相似度（浏览器 / 油猴）

### 关键结论：bge-small-zh-v1.5 的真实体积（逐文件核实）

来自 HuggingFace 文件 API（`Xenova/bge-small-zh-v1.5`，onnx 目录共 348 MB，含全部精度）：

| 文件 | 体积 |
|---|---|
| `onnx/model.onnx`（fp32） | **94.85 MB** |
| `onnx/model_fp16.onnx` | 47.50 MB |
| `onnx/model_quantized.onnx`（q8，transformers.js 默认） | **24.01 MB** |
| `onnx/model_int8.onnx` | 23.90 MB |
| `onnx/model_uint8.onnx` | 23.90 MB |
| `onnx/model_q4.onnx` | 52.40 MB |
| `onnx/model_q4f16.onnx` | 29.40 MB |
| `tokenizer.json` + `vocab.txt` | 0.44 MB + 0.11 MB |

**架构（`BAAI/bge-small-zh-v1.5` config.json 原文）**：4 层 Transformer、hidden 512、8 头、intermediate 2048、`max_position_embeddings` 512、词表 21128 → 约 24M 参数。

**所以：q8 量化后就是 24 MB 一个文件**（+0.5 MB 词表），这是能在油猴里落地的量级。

**（2）加载方式（transformers.js v3）**
```js
import { pipeline } from '@huggingface/transformers';
const pipe = await pipeline('feature-extraction', 'Xenova/bge-small-zh-v1.5', {
  dtype: 'q8',        // 对应 model_quantized.onnx，24MB
  device: 'wasm',     // 24M 小模型用 webgpu 收益有限，wasm 更稳
});
const out = await pipe(['文本1', '文本2'], { pooling: 'mean', normalize: true });
```
- `dtype` 可选 `fp32 / fp16 / q8 / int8 / uint8 / q4 / bnb4 / q4f16`（官方 dtypes 指南）。
- 官方文档：https://huggingface.co/docs/transformers.js/v3.8.1/guides/dtypes
- 模型卡：https://huggingface.co/Xenova/bge-small-zh-v1.5

**（3）推理速度：只能给你量级，必须自测**
- 24M 参数、4 层、512 维，编码一条 ≤64 token 的中文短句：桌面 Chrome（WASM + SIMD + 多线程）通常在**数十毫秒**量级；手机端慢 3–10 倍；首次还要加上 24 MB 模型下载 + 初始化（几百 ms 到数秒）。
- 上述是**基于模型规模的量级估计，不是实测值**——我在检索中没有找到可信的浏览器端 bge-small-zh 速度基准。**上线前请用 `performance.now()` 在目标机型上测 100 次取 P50/P95。**
- 优化：`dtype: 'q8'`、短文本截断到 64 token、批量成 8–16 条一次 forward、模型与向量缓存进 IndexedDB / Cache API。

**（4）替代方案对比（均已核实存在与规格）**

| 模型 | 参数 | 维度/层数 | ONNX 现成？ | 许可 | 评价 |
|---|---|---|---|---|---|
| **BAAI/bge-small-zh-v1.5**（Xenova 转换） | ~24M | 512 / 4 | ✅ 单文件，q8 24 MB | MIT（以模型卡为准） | **首选**，体积/效果平衡最好，中文语义相似度强 |
| moka-ai/m3e-small | 24M | 512 | ❌ 无官方 transformers.js 版，需自己 `optimum` 导出 | **非商用**（训练数据含非商用集） | 效果与 bge-small 接近（s2s 0.5834），但许可是硬伤 |
| shibing624/text2vec-base-chinese | **102.3M** | 768 | ✅ 仓库自带 `onnx/model.onnx` 与 `model_qint8_avx512_vnni.onnx` | **Apache-2.0** ✅ | 可商用，但 102M 在浏览器里偏重（q8 约 100 MB 级） |
| thenlper/gte-small-zh | ~30M | 512 / 6 | ❌（HF 上 `thenlper/gte-small-zh` 已 404，仅见 `towing/gte-small-zh` 镜像） | 未核实 | 6 层，比 bge-small 略重，无现成 ONNX，不建议 |
| 纯算法方案（无模型） | 0 | — | — | — | **SimHash / MinHash + 字符 n-gram Jaccard**，处理「复制粘贴/模板化」足够 |

**（5）一个容易踩的坑**：`onnx-community/bge-small-zh-v1.5-ONNX`（2026-01 版）用的是**外置权重**（`model_quantized.onnx` 仅 168 KB + `model_quantized.onnx_data` 23.77 MB）。浏览器/油猴场景请**用 Xenova 的单文件版**，否则要多写一层自定义 fetch 逻辑。两种版本的 q8 总大小一致（≈23.9 MB）。

### 可落地建议
1. **别一上来就上模型**：`SimHash`（近重复）+ `字符 2-gram Jaccard`（模板化）能解决 80% 的「水军重复文本」，成本近乎为零。
2. **语义模型只用来做一件事**：判断「这条评论是否在复述/影射某条已有评论」（同义改写），输入两条文本、输出余弦相似度。
3. **用 Xenova 单文件 q8（24 MB）+ `device:'wasm'`**；`wasmPaths` 指向你自己的 CDN/扩展内路径，避免 CSP 与离线失败。
4. **bge 的中文检索指令只在「检索」场景加**（`为这个句子生成表示以用于检索相关文章：`）；句-句相似度不需要加，加了反而要成对一致。
5. **加降级路径**：模型加载失败/超时 → 自动退回 SimHash + 词表，绝不能让判定逻辑整体挂掉。

## 6. 中文停用词 / 语气词 / 网络流行语词表

### 关键结论

**（1）停用词表：有四个主流版本，一次拿全**
- GitHub `goto456/stopwords`：`cn_stopwords.txt`（中文停用词表）、`hit_stopwords.txt`（哈工大）、`baidu_stopwords.txt`（百度）、`scu_stopwords.txt`（四川大学机器智能实验室）。链接：https://github.com/goto456/stopwords
- **⚠️ 用法警告**：这些表是「删词」用途，**里面包含连词与否定词**（但是、然而、不、没…）。做第 4 节的 cue 判定时，**必须从停用词表里把这些词捞出来单独建白名单**，否则删词=删信号。

**（2）情感/否定/程度副词词表**：HowNet《情感分析用词语集》（否定词、程度副词、主张词等）；打包版见 GitHub `DavionWu2018/Sentiment_dictionary`（中文情感词典 + 停用词 + 程度副词 + 否定词表 + 金融情感词典）。

**（3）转折/连接词表**：Chinese-DiMLex（137 个，PDTB 3.0 语义关系，XML），见第 4 节。

**（4）辱骂/攻击词表（可直接并入）**：ToxiCN 1,032 词（CC BY-NC-ND，仅研究用）；SexHateLex 3,016 词（CC BY 4.0，可商用）。两者互补：前者含隐性侮辱，后者覆盖面广。

**（5）B 站特有的梗/弹幕黑话**：
- `bilibili-API-collect` 的弹幕名词解释文档（`danmaku/buzzword.md`）——社区维护的 B 站黑话/梗词条，最贴近站内实际用法。仓库：https://github.com/SocialSisterYi/bilibili-API-collect
- 梗百科类词库（如 `thawline/dsh-memewiki` 收录 6,668 条梗/黑话）——可作为补充，但需自行校验质量与许可。
- 官方/半官方渠道：B 站每年发布的年度弹幕（可用于「当年流行语」的时间切片）。

**（6）语气词清单（自建，用于「软化/讥讽」特征）**
- 句末：啊、呀、哇、吧、呢、吗、嘛、呗、啦、咯、噢、哟、嗯、哎、诶
- 限定/轻描淡写：罢了、而已、就是了、顶多、也就
- 笑声：呵、呵呵、哈哈、哈哈哈、嘿嘿、嘻嘻、噗
- 用法：`罢了/而已/就是了` + 前面是负面评价 → 阴阳怪气加分；`呢/哦/呀` 出现在陈述句末且句中有夸张褒义 → 反讽加分。

### 可落地建议
1. **建三张独立表，不要混在一张停用词表里**：`stopwords`（删词用）、`cue_words`（否定/转折/转述，判定用）、`slang`（流行语/梗，加权用）。
2. **所有词表都带 `version` + `updated_at` 字段并支持热更新**：网络流行语半衰期约 3–6 个月，硬编码在脚本里必然过期。
3. **记录命中日志**：每条规则命中的原词、上下文 20 字、用户是否申诉，按月回捞新词——这是词表能持续进化的唯一现实路径。
4. **梗词表分「褒/贬/中性」三档标注**，因为同一个词（如「典」「孝」「赢」）在不同语境下极性完全相反，只按词命中会大量误判。
5. **B 站专属词单独一个文件**：`bilibili-API-collect` 的 buzzword 文档可作起点，避免把贴吧/微博的梗混进来。

## 附：整体落地架构建议（三层，逐层加成本）

```
第 1 层（必做，纯规则，<5ms）
  词表命中（ToxiCN/SexHateLex + 阴阳怪气词表 + B站梗）
  + 作用域判定（引号 / 否定 cue / 转折后主张区）
  + 账号规则（昵称正则 / 等级 / 频率 / 默认头像）
       ↓ 输出：证据列表 + 分数
第 2 层（建议做，纯算法，<20ms）
  SimHash 近重复 + 字符 n-gram Jaccard（水军/控评）
  + 时间局部性（同视频 5 分钟窗口）
       ↓
第 3 层（可选，需模型，首次 24MB 下载）
  bge-small-zh-v1.5 q8 语义相似度（同义改写 / 字面义 vs 上下文义反讽）
       ↓
输出：只做「折叠 + 展示证据 + 一键展开」，拉黑由用户二次确认
```

三条硬约束：
1. **不做单条判决**，所有结论必须带上下文（父评论/视频标题）——2609.04384 的 39 个百分点是这一条的依据。
2. **不做自动拉黑**，只做排序与折叠，最终动作交给用户。
3. **每一条判定都要能解释**（命中什么词、什么规则、什么上下文），否则用户不会信任，工具活不过一个月。
